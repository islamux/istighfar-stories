01 · Overview

The problem & the motivation

The problem
  • Inspirational Islamic story content about istighfar is scattered and usually Arabic-only.
  • When translated, the reading experience is often an afterthought — especially RTL layout and Arabic typography.
  • Audiences switch languages; the app must mirror perfectly between RTL and LTR.
  • Readers are often offline or on slow networks — assets must be self-hosted and optimized.
The motivation
  • Build a polished, production-ready bilingual experience — not a toy.
  • Use authenticity as a design constraint: classic Arabic calligraphy (Amiri) for story titles, modern geometry (Cairo) for UI.
  • Treat this as a portfolio that shows real engineering artifacts — plans, migration docs, convention commits.
  • Prove next-gen React patterns (App Router, Server Components, React 19 idioms) in a real app.

The story data itself: 11 bilingual stories curated from the Islamic tradition, categorized across 5 themes, shipped as structured TypeScript.

01 · Overview

Features at a glance

Bilingual toggle

One state variable switches ar ↔ en — stories, categories, UI strings, fonts, and text direction flip together.

Full RTL / LTR

Document is root-dir="rtl"; components mirror via dir, logical alignment, and flex flips.

5 categories

Repentance, gratitude, patience, forgiveness, mercy — color-coded badges with light & dark variants.

Category filtering

Responsive grid

1 → 2 → 3 columns, line-clamp titles/excerpts, hover elevation & shadow transitions.

Search, story-detail pages, and URL-based locale routing are planned — see the Known Gaps slide.

03 · Data Layer

Typed story model — make invalid states unrepresentable

export type StoryCategory = 'repentance' | 'gratitude'
  | 'patience' | 'forgiveness' | 'mercy';
export type Language = 'ar' | 'en';

interface StoryTranslation {
  title: string; content: string; excerpt: string;
}

interface Story {
  id: string;
  category: StoryCategory;   // unions a free-string bug at build time
  source: string;
  author?: string;             // optional — not every story is attributed
  date: string;
  readTime: number;             // minutes, derived by the parser
  translations: Record<Language, StoryTranslation>;
  // ↑ a total map: 'ar' AND 'en' are required — the compiler checks it
}
// Categories ship bilingual labels for the same union type
export const CATEGORIES: CategoryLabel[] = [
  { id: 'repentance', labelAr: 'التوبة',  labelEn: 'Repentance' },
  { id: 'gratitude', labelAr: 'الشكر',    labelEn: 'Gratitude' },
  { id: 'patience',  labelAr: 'الصبر',    labelEn: 'Patience' },
  { id: 'forgiveness', labelAr: 'المغفرة', labelEn: 'Forgiveness' },
  { id: 'mercy', labelAr: 'الرحمة', labelEn: 'Mercy' },
];
Why this model wins
  • One source of truth per story — the story owns both languages; views just pick story.translations[language].
  • Record<Language, StoryTranslation> is a total map — adding a story with a missing language is a compile error, not a runtime surprise.
  • Category is a string-literal union — typos like 'repetance' fail at build time.
  • Presentation data derived upstream: readTime is computed by the parser (words ÷ 200 wpm), not hand-maintained.
Current content
  • 11 stories, ids '1'–'11', fully bilingual.
  • Categories today: repentance 10gratitude 1
  • Source lineage documented: stories-md/ markdown files.

04 · i18n & RTL

Translation layer — data-driven, today

const [language, setLanguage] =
  useState<Language>('ar');
const isRtl = language === 'ar';

<div dir={isRtl ? 'rtl' : 'ltr'}
     className={isRtl ? 'font-arabic' : 'font-sans'}>
  <button onClick={() => setLanguage('ar')}>العربية</button>
  <button onClick={() => setLanguage('en')}>English</button>
</div>

UI strings use inline ternaries; categories use labelAr/labelEn; content uses story.translations[language].

Why this design (for now)
  • Zero routing complexity — switching is a state change, no navigation or cache refetch.
  • Compile-time completeness — the type system guarantees both languages on every story.
  • Right-sized for 11 stories — a full locale pipeline would be speculative complexity (YAGNI).
The upgrade path — when scale demands it
  • Move UI strings to locale files (locales/ar.json, en.json) + a typed dictionary.
  • Adopt URL-based locale segments (/en/…, /ar/…) for per-language SEO & caching.
  • Use a standard lib (next-intl) for pluralization, formatting, and locale middleware.
  • Keep dir / font logic — that work is already separated and reusable.
04 · i18n & RTL

RTL engineering & Arabic typography

Direction handling

  • Root document: <html lang="ar" dir="rtl"> — SSR output is RTL-first.
  • Container dir flips for free: flex order, grid flow, text alignment, inline start/end.
  • Where automatic flipping isn't enough we flip explicitly: flex-row-reverse, order-first, mr-auto ⇄ ml-auto.
  • Read-time badge uses order-first so the visual rhythm stays correct in both directions.

Typography strategy

RoleFontWhy
Headings / story titlesAmiri (classic Naskh calligraphy)Authentic Islamic reading feel
UI / bodyCairo (modern geometric)Clean, readable, contemporary
export const amiri = Amiri({

  weight: ['400', '700'],
  variable: '--font-amiri',     // exposed as a CSS var
  display: 'swap',              // no invisible text (FOIT)
  preload: true,
});

  subsets: ['arabic'],
  weight: ['400','500','600','700'],

  display: 'swap', preload: true,

.font-arabic { /* Amiri for narrative */

}
.font-arabic-ui { /* Cairo for UI */

Theming architecture
  • next-themes with attribute="class", defaultTheme="system", enableSystem.
  • CSS-variable driven: :root = light tokens, .dark overrides, mapped to Tailwind via @theme inline.
  • No FOUC / flash of wrong theme: color-scheme set per theme + suppressHydrationWarning.
  • Accessible: the toggle exposes a detailed aria-label describing current vs. system theme.

05 · Theming & Performance

Performance — defaults chosen deliberately

Static by default

The app has no dynamic data — no DB, no API, no cookies in content. Every page is pre-rendered at build time; CDN edge serves static HTML.

Fonts, optimized

next/font self-hosts at build, serves Arabic subsets only, sets display: swap → near-zero FOIT, works offline. ~220 KB font budget documented in the plan.

Small client JS

Only two client islands (StoryList, ThemeToggle) hydrate; the rest of the tree stays server-rendered. Filter/language work happens without network round-trips.

Rendering discipline

Titles/excerpts use line-clamp to keep cards uniform; scroll-behavior: smooth; CSS-only theme transition (0.2s) avoids reflow-heavy JS.

07 · Interview Q&A — Rendering & React

Rendering & React — expected questions

Why Next.js instead of Vite + React or a static site generator?
  • I get SSG/SSR/CSR/ISR under one framework; here SSG at build time is a zero-cost default because there's no request-dependent data.
  • Server Components mean my content model is typed at the source, nearest to the data — no 'fetch-then-render' ceremony.
  • Built-ins I actually use: next/font, Metadata API, file-based routes. A Vite SPA would re-implement routing, SEO metadata, and font optimization.
  • Answer length: 30s. Don't list every feature — tie to THIS app.
Explain how you split Server vs Client components — what's your rule?
  • The smallest interactive island. A component is a Client Component only if it holds state, handles events, or uses browser APIs (theme, scroll).
  • StoryList (language + filter state), ThemeToggle, ThemeProvider are marked 'use client'. Everything else renders on the server.
  • Consequence: StoryCard stays server-renderable — a pure presentational component I could even extract to a shared UI package.
  • This minimizes hydration work and keeps most of the page as static HTML.
What is hydration, and what hydration pitfalls did you handle?
  • Hydration = React re-running the component tree in the browser on top of server-generated HTML and attaching event handlers/state.
  • Pitfall 1 — theme FOUC/mismatch: the server doesn't know the visitor's system theme; solved with next-themes + suppressHydrationWarning + rendering a skeleton until mounted.
  • Pitfall 2 — mounted-state: I avoid useEffect for "am I mounted?" and use useSyncExternalStore instead — server snapshot false, client snapshot true, so server and first client render agree.
Why is the language state client-side rather than URL-based / server-side?
  • This scale: switching must be instant; a route change + re-fetch is unnecessary since content lives in the bundle and both locales ship.
  • Downside admitted: no per-locale URLs → weaker SEO, no deep-linking a language. The upgrade path (locale segments via next-intl) is designed and documented.
  • Decision was deliberate: optimize for UX now, SEO when the story count justifies it — a YAGNI call.
React 19 — anything you use that wasn't available before?
  • Server Components are the biggest shift I leverage daily (RSC is the default in the App Router).
  • useSyncExternalStore for hydration-safe mounted detection — a first-class API replacing a useEffect workaround.
  • The upgrade to Next 16 brought React 19 into the whole toolchain (types, lint, Tailwind v4 pairing).
07 · Interview Q&A — Tailwind, RTL, Performance

Tailwind, RTL, & performance — expected questions

Tailwind v4 is CSS-first — how is that different, and do you like it?
  • v3: tailwind.config.js + JS-extracted theme. v4: CSS-first — @import "tailwindcss", theme defined via @theme, native CSS variables everywhere.
  • I map semantic tokens once: @theme inline { --color-primary: var(--primary); } → then write utilities like bg-primary that follow the actual CSS variable, so dark mode is just a variable swap.
  • Build is now a single PostCSS plugin (@tailwindcss/postcss), no config file churn. Prefer it — less tooling indirection.
How does next/font beat a Google Fonts <link>?
  • next/font self-hosts at build → no runtime third-party request (privacy + reliability), files go through Next's caching/CDN.
  • I subset to Arabic glyphs only, preload critical weights, and set display: swap → no invisible text while loading.
  • Fonts are hashed and load with the page's own network priorities — measurable on Lighthouse font metrics.
What specifically breaks in RTL if you only mirror the CSS?
  • "Mirroring" fails at direction vs. block flow: with dir="rtl" the inline axis flips but vertical layout doesn't — so flex/grid auto-flip is usually right, but explicit margins/absolute positioning don't follow.
  • Padding/margins should use logical properties (ms-*/me-*, ps-*/pe-*) not physical (ml/mr). I flip the story footer with flex-row-reverse + order-first where direction alone isn't enough.
  • Line-height and letter-spacing choices differ for Arabic script — a reason typography gets its own documented plan.
Your performance wins — rank them by impact.
  • 1. Static rendering — the whole page is HTML at the edge, nothing to fetch/render per request.
  • 2. Small hydration surface — two client islands ≈ minimal JavaScript on the wire.
  • 3. Font subsetting + swap — removes render-blocking FOIT for Arabic text (LCP-affecting).
  • 4. Self-hosted assets — offline, no external dependency for core visuals.
How would you scale this to 10,000 stories?
  • Data: move markdown → a content source (CMS / content layer like Contentlayer or MDX remote), or filesystem collection with caching.
  • Rendering: per-story generateStaticParams + ISR — revalidate only changed stories instead of a full build; add search (edge index, e.g. Meilisearch/Typesense) and pagination.
  • i18n: switch to URL locale segments so each language is its own cacheable static set.
  • Images: per-story OG images generated at build. Content pipeline becomes the release gate (parser + validation + typed output).
07 · Interview Q&A — Design & Behavioral

System design & behavioral — expected questions

Add user accounts + "saved stories". What's your plan?
  • Auth: NextAuth/Auth.js with email + OAuth; server-side session cookie; protect the saved-stories API.
  • Data: a relational model — User ↔ SavedStory (userId, storyId, createdAt); no user PII in story content.
  • Architecture: keep the story catalog static/cached; only saved-stories is dynamic → a single route group with per-user data keeps the static story pages untouched. Rationale: don't turn a static site dynamic globally for one feature.
Full i18n routing — walk me through the migration.
  • Restructure to app/[locale]/… with a next-intl middleware detecting Accept-Language and cookie; always redirect to a locale-prefixed URL (/ar/…, /en/…).
  • Keep my current model: stories carry both translations — only UI strings move to locale dictionaries. Content locale comes from the URL segment, not client state.
  • Add hreflang + alternate links for SEO parity between locales; set lang/dir per route segment.
  • Testing matrix: RTL×LTR × light×dark × each locale — every combination is a screenshot edge case.
How do you QA bilingual + RTL + theming combinations automatically?
  • Parser unit tests first (frontmatter variants, missing sections, Arabic keyword inference) — the content pipeline is the riskiest untested code today.
  • Component tests (Vitest + Testing Library) for StoryList and ThemeToggle: language toggle, filter logic, mounted skeleton.
  • Visual regression (Playwright snapshots) across a matrix of dir × theme × viewport — this is what actually catches RTL/LTR asymmetry I shipped by hand.
Tell me about a design decision you made, then changed.
  • Example: I chose client-side language state to ship fast and keep switching instant. Revisiting for SEO/publishing, I'd move to URL locale segments.
  • Why it's defensible: the constraint was prototype velocity + type safety; the design kept UI strings, category labels, and content lookup separable, so the migration is localized rather than a rewrite.
  • I write decision records (docs/) precisely so I can revisit a choice with its original reasoning intact.
You have 3 months. What do you build next, in order?
  • Weeks 1–4: story-detail pages + per-story SEO + OG images; convert the 2 remaining markdown files; add parser unit tests.
  • Weeks 5–8: locale-URL i18n migration + search; both unlock the app's reach.
  • Weeks 9–12: visual regression suite, PWA offline reading (the pwa-branch), then ship a public content pipeline so contributors add stories via PR.
